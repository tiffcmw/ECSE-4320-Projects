# Hypotheses (written before any benchmark was run)

Written 2026-10-06 in Phase 0. No kernel has been timed at this point. Each hypothesis has a verdict column that will be filled in after the results exist. Verdict values: supported, partly supported, refuted, pending.

Assumptions behind the numbers (all from public knowledge of Apple big cores, not measured here, so they are themselves hypotheses): 4 NEON FP pipes of 128 bits each, 3 load ports and 2 store ports per cycle, clock about 4 to 4.5 GHz on the fastest tier, 128 B cache lines, DRAM bandwidth for a single thread well below the chip total.

Notation: lanes L = 4 (fp32), 2 (fp64), 4 (int32). AI = flops per byte moved (compulsory traffic, write-allocate ignored unless stated).

| ID | Hypothesis | Reason | Verdict |
|----|-----------|--------|---------|
| H1 | Scalar-baseline vs auto-vectorized speedup for SAXPY, multiply and stencil in L1 is between 2.5x and 4x for fp32 and between 1.5x and 2x for fp64, below the lane count. | The scalar loop is already unrolled and issues several scalar FMAs per cycle, but the load/store ports and loop overhead cap it. Vector loads move 16 B per op instead of 4 B. | pending |
| H2 | Speedup compresses to 1.0x to 1.3x for working sets larger than the SLC (DRAM resident). | Both versions wait on the same memory system; a scalar loop can already saturate a single core's DRAM bandwidth via hardware prefetch. | pending |
| H3 | SIMD gain begins to compress at the L2 boundary (8 to 16 MiB), not at L1, and is mostly gone by 4x the SLC size. | L2 bandwidth per core is high but finite (roughly 2 to 4 x 16 B per cycle at most) and the scalar loop stops being instruction bound as soon as bytes per cycle drop below its issue limit. | pending |
| H4 | The float32 dot product does NOT auto-vectorize under plain -O3 (the speedup vs scalar baseline is about 1.0x). It vectorizes with -ffast-math and then gains 2x to 4x in L1 (limited by the 4-cycle FMA latency unless the compiler uses multiple accumulators). | Reassociation changes rounding, so clang refuses without a fast-math flag. | pending |
| H5 | Fast-math dot product differs from the long double reference by a few ulps (relative error roughly 1e-7 to 1e-6 for N = 1e6, fp32), while the scalar sequential sum has error growing about with sqrt(N) times eps; a vectorized partial-sum order is typically no worse and often better. | Pairwise-like lane splitting shortens the accumulation chain. | pending |
| H6 | Elementwise multiply behaves like SAXPY at the same working set but with lower AI (1 FLOP per 12 B vs 2 per 12 B), so it hits the memory ceiling at the same size and has the same speedup curve. | Same bytes per element, half the flops. | pending |
| H7 | The 3-point stencil auto-vectorizes (unaligned loads at x[i-1], x[i+1]) and has speedup close to SAXPY in cache. | Unaligned vector loads are cheap on Apple cores. | pending |
| H8 | fp64 speedup over its own scalar baseline is about half that of fp32 in cache (lane count 2 vs 4), and in DRAM fp64 and fp32 have equal throughput in GiB/s but fp64 has half the elements per second. | Lane count and bytes per element. | pending |
| H9 | int32 elementwise ops speed up about like fp32 in cache; int32 multiply may be slightly slower than fp32 multiply per lane (NEON mul.4s throughput). | Same lanes and bytes; different pipe usage. | pending |
| H10 | Alignment: shifting the array start by 0, 4, 8, 16, 32 B changes SAXPY throughput by less than 5% in L1/L2. Offsets that create a cache-line (128 B) or 16 KiB page crossing on every vector access are not reachable by simple offsets, but the 60 B offset (not a multiple of 16) and 64 B offset will show 0 to 15% penalty at most. | Apple cores handle misaligned vector accesses in hardware with a small penalty only when an access straddles a line boundary. | pending |
| H11 | Tail cost: for N < 64 elements the per-element cost is 3x to 10x higher than at N = 4096, and N not divisible by 4 (or by the unroll factor times 4) adds 1 to 3 scalar epilogue iterations whose relative cost is visible only at small N (under about 5% above N = 256). | Fixed loop entry, prologue checks and epilogue dominate short loops. | pending |
| H12 | Stride: stride-2 and stride-4 SAXPY are scalar or use ld2/ld4 style de-interleave and show useful-bandwidth (GiB/s of elements actually used) falling to about 1/2 and 1/4 of unit stride when data is beyond L1, because whole 128 B lines are fetched. Stride 8 and the index gather fall to about 1/8 or lower in DRAM, and the SIMD speedup over scalar is about 1.0x for gather. | Line-granular transfers; there is no gather instruction in NEON, so gather is scalar loads. | pending |
| H13 | A single-thread STREAM triad measures about 60 to 120 GB/s on this chip (not the 400+ GB/s chip aggregate), and the roofline memory ceiling for one thread is that figure. | A single core's outstanding-miss capacity bounds its bandwidth (Little's law). | pending |
| H14 | FMA throughput benchmark: latency about 3 to 4 cycles, saturation at about 12 to 16 independent accumulators, indicating 4 FP pipes (peak about 16 fp32 FMA lanes per cycle = 32 FLOP/cycle, around 130 to 150 GFLOP/s fp32 single-thread). | Little's law: pipes x latency accumulators needed. | pending |
| H15 | Roofline: SAXPY (AI = 2/12 = 0.167 FLOP/B fp32) and dot product (AI = 2/8 = 0.25 FLOP/B fp32) lie far left of the ridge point (ridge about 1.5 to 2.5 FLOP/B) and are memory bound everywhere beyond L2. In L1 they are limited by load/store throughput, not the FLOP ceiling, so they sit under a cache-level bandwidth roof. | AI is far below peak FLOP / DRAM BW. | pending |
| H16 | Negative case A: float reduction without fast-math emits a "loop not vectorized: cannot prove it is safe to reorder floating-point operations" remark, the disassembly shows scalar fadd/fmadd, and timing equals the scalar build (ratio 0.95 to 1.05). With -ffast-math the speedup is 2x to 4x in L1. | See H4. | pending |
| H17 | Negative case B: SAXPY beyond the SLC with SIMD gives 1.0x to 1.3x over scalar although the vector code is perfectly vectorized. | See H2. | pending |
| H18 | Naive benchmark mistakes (loop hoisted/removed, cache-resident "DRAM" arrays, first-touch page faults in the timed region) produce numbers that are unphysical (for example bandwidth above the L1 limit, or implausibly low time per element) and the corrected benchmark differs by more than 3x in at least one case. | Compiler dead-code elimination and reuse. | pending |
| H19 | Run-to-run noise: median-of-15 coefficient of variation is under 3% in cache and under 8% in DRAM, if the harness thread runs at user-interactive QoS on a Super core. A bimodal distribution, if present, indicates placement on a Performance core. | macOS cannot pin threads; QoS biases only. | pending |
| H20 | Native build (-mcpu=apple-m4 via native) is within 5% of the default auto build for these kernels. | Default arm64 target already includes NEON, FMA; the CPU-specific change mostly alters scheduling. | pending |

## How verdicts will be assigned

Supported: measured value falls inside the stated range. Partly supported: trend correct but value outside range or only for some dtypes/kernels. Refuted: trend or value contradicts the statement. Anomalies are recorded with a plausible cause marked unverified.
