# Hypotheses (written before any benchmark was run)

Written 2026-10-06 in Phase 0. No kernel has been timed at this point. Each hypothesis has a verdict column that will be filled in after the results exist. Verdict values: supported, partly supported, refuted, pending.

Assumptions behind the numbers (all from public knowledge of Apple big cores, not measured here, so they are themselves hypotheses): 4 NEON FP pipes of 128 bits each, 3 load ports and 2 store ports per cycle, clock about 4 to 4.5 GHz on the fastest tier, 128 B cache lines, DRAM bandwidth for a single thread well below the chip total.

Notation: lanes L = 4 (fp32), 2 (fp64), 4 (int32). AI = flops per byte moved (compulsory traffic, write-allocate ignored unless stated).

| ID | Hypothesis | Reason | Verdict |
|----|-----------|--------|---------|
| H1 | Scalar-baseline vs auto-vectorized speedup for SAXPY, multiply and stencil in L1 is between 2.5x and 4x for fp32 and between 1.5x and 2x for fp64, below the lane count. | The scalar loop is already unrolled and issues several scalar FMAs per cycle, but the load/store ports and loop overhead cap it. Vector loads move 16 B per op instead of 4 B. | refuted (f32 vs unroll8: SAXPY 2.1x, mul 2.2x, stencil 2.9x, below the 2.5-4x range for SAXPY and mul; f64 1.07x, below 1.5-2x; vs the spec `scalar` build 5.2x f32, above lane count) - plots/exp1_sweep_f32.png, exp1_sweep_f64.png |
| H2 | Speedup compresses to 1.0x to 1.3x for working sets larger than the SLC (DRAM resident). | Both versions wait on the same memory system; a scalar loop can already saturate a single core's DRAM bandwidth via hardware prefetch. | partly supported (f32 SAXPY 1.35x, mul 1.17x, f64 SAXPY 1.02x vs unroll8 at 1 GiB; range 1.0-1.3x; but 3.0x vs the spec scalar build) - data/processed/exp1_speedup_phase3.csv |
| H3 | SIMD gain begins to compress at the L2 boundary (8 to 16 MiB), not at L1, and is mostly gone by 4x the SLC size. | L2 bandwidth per core is high but finite (roughly 2 to 4 x 16 B per cycle at most) and the scalar loop stops being instruction bound as soon as bytes per cycle drop below its issue limit. | refuted (the compression happens at the L1 boundary (128 KiB) for SAXPY, a cliff from 2.1x to 1.35x; mul decays between 128 KiB and 2 MiB; no feature at the 16 MiB L2 boundary or anywhere beyond) - plots/exp2_saxpy_locality.png |

| H12 | Stride: stride-2 and stride-4 SAXPY are scalar or use ld2/ld4 style de-interleave and show useful-bandwidth (GiB/s of elements actually used) falling to about 1/2 and 1/4 of unit stride when data is beyond L1, because whole 128 B lines are fetched. | H14 | FMA throughput benchmark: latency about 3 to 4 cycles, saturation at about 12 to 16 independent accumulators, indicating 4 FP pipes (peak about 16 fp32 FMA lanes per cycle = 32 FLOP/cycle, around 130 to 150 GFLOP/s fp32 single-thread). | Little's law: pipes x latency accumulators needed. | pending |

## How verdicts will be assigned

Supported: measured value falls inside the stated range. Partly supported: trend correct but value outside range or only for some dtypes/kernels. Refuted: trend or value contradicts the statement. Anomalies are recorded with a plausible cause marked unverified.

## Pilot disclosure (added after the Phase 1 smoke run, 2026-10-06)

The rows above were written first and are not edited. During Phase 1 a smoke run (`data/raw/smoke_phase1.csv`, `data/raw/smoke_phase1_unroll.csv`; 3 sizes, 15 samples per point) was executed to validate the harness. It was not an experiment, but it exposed facts that bear on several hypotheses, so they are disclosed here. Verdicts are left to the real experiments.

1. The assignment-defined scalar build (`-O3 -fno-vectorize -fno-slp-vectorize`) is not unrolled by clang for these loops: `scalar` and `scalar_nounroll` timed identically (about 1 loop iteration per cycle). H1 assumed an unrolled scalar loop. An explicit scalar build with `#pragma clang loop unroll_count(8)` (`scalar_unroll8`) is faster (SAXPY f32, N = 4096: 561 ns vs 899 ns per call). Speedups will be reported against `scalar_unroll8` as the primary (conservative) baseline and against `scalar` as secondary.
2. Plain `-O3` does vectorize the f32 dot product (remark: vectorization width 4, interleaved count 4), but with a strict in-order reduction, so the adds remain a serial chain. H4 and H16 assumed no vectorization at all. The statement to test becomes: vectorized, but no better than latency bound.
3. SAXPY f32 at a 1 GiB working set reached about 149 GiB/s from one thread with the vector build, higher than the 60 to 120 GB/s assumed in H13, and a 4 MiB (L2-sized) point showed about the same bandwidth. The locality sweep will examine this.

No hypothesis text was changed in response to these observations.

## Addendum, written after Phase 2 disassembly and before Experiment 3 (2026-10-06)

The disassembly of the auto SAXPY (`vecreports/VECTORIZATION.md`) shows three code paths: scalar only for N < 4, a 4-element vector loop for 4 <= N < 16, and a 16-element main loop followed by the 4-element loop and a scalar loop. Predictions for the tail study (refines H11):

| ID | Hypothesis | Verdict |
|----|-----------|---------|
| H11b | Time per element for N = 16k + r is lowest for r = 0 and rises with the number of epilogue iterations: r in 1..3 (scalar tail only) costs more than r in 4..12 that are multiples of 4, and r that mixes both a 4-element step and scalar steps is the worst. The sawtooth is visible below N of about 256 and fades above N of about 1024. | pending |
| H11c | Time per call is an affine function of N for N >= 16 with an intercept (fixed cost: entry checks plus call) of about 5 to 15 ns at 4.58 GHz (24 to 70 cycles). | pending |
| H21 | `auto_norestrict` SAXPY is within 10% of `auto` for non-overlapping arrays at large N (runtime check is a one-time cost), but is measurably slower for N below about 64 because of the check and branch. When the arrays are made to overlap by one element (y = x + 1), the runtime check sends execution to the scalar path and the speed falls to the scalar-build level. | pending |
