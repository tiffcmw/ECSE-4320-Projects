# Hypotheses (written before any benchmark was run)

Written 2026-10-06 before any benchmark was run. No kernel has been timed at this point. Each hypothesis has a verdict column that will be filled in after the results exist. Verdict values: supported, partly supported, refuted, pending.

Assumptions behind the numbers (all from public knowledge of Apple big cores, not measured here, so they are themselves hypotheses): 4 NEON FP pipes of 128 bits each, 3 load ports and 2 store ports per cycle, clock about 4 to 4.5 GHz on the fastest tier, 128 B cache lines, DRAM bandwidth for a single thread well below the chip total.

Notation: lanes L = 4 (fp32), 2 (fp64), 4 (int32). AI = flops per byte moved (compulsory traffic, write-allocate ignored unless stated).

## How verdicts will be assigned

Supported: measured value falls inside the stated range. Partly supported: trend correct but value outside range or only for some dtypes/kernels. Refuted: trend or value contradicts the statement. Anomalies are recorded with a plausible cause marked unverified.

## Smoke-run disclosure (added after the first smoke run, 2026-10-06)

The rows above were written first and are not edited. During harness validation a smoke run (`data/raw/smoke_phase1.csv`, `data/raw/smoke_phase1_unroll.csv`; 3 sizes, 15 samples per point) was executed to validate the harness. It was not an experiment, but it exposed facts that bear on several hypotheses, so they are disclosed here. Verdicts are left to the real experiments.

1. The default scalar build (`-O3 -fno-vectorize -fno-slp-vectorize`) is not unrolled by clang for these loops: `scalar` and `scalar_nounroll` timed identically (about 1 loop iteration per cycle). H1 assumed an unrolled scalar loop. An explicit scalar build with `#pragma clang loop unroll_count(8)` (`scalar_unroll8`) is faster (SAXPY f32, N = 4096: 561 ns vs 899 ns per call). Speedups will be reported against `scalar_unroll8` as the primary (conservative) baseline and against `scalar` as secondary.
2. Plain `-O3` does vectorize the f32 dot product (remark: vectorization width 4, interleaved count 4), but with a strict in-order reduction, so the adds remain a serial chain. H4 and H16 assumed no vectorization at all. The statement to test becomes: vectorized, but no better than latency bound.
3. SAXPY f32 at a 1 GiB working set reached about 149 GiB/s from one thread with the vector build, higher than the 60 to 120 GB/s assumed in H13, and a 4 MiB (L2-sized) point showed about the same bandwidth. The locality sweep will examine this.

No hypothesis text was changed in response to these observations.

## Addendum 2, written after the strided and gather kernels were compiled and inspected, before Experiments 3 and 4 were run (2026-10-06)

Inspection of the compiler output (`vecreports/summary.md`, remarks for `saxpy_s*` and `gather`) shows that at strides 2 to 32 and for the gather the default `auto` build does not vectorize ("the cost-model indicates that vectorization is not beneficial", it only interleaves the scalar loop 4x), and that the `auto_forcevec` build (`#pragma clang loop vectorize(enable)`) vectorizes using `ld2.4s` de-interleave at stride 2, 2-lane `zip1` code at stride 8, and lane-by-lane `ld1.s {v}[n]` for the gather, always with scalar or lane stores (NEON has no scatter). Predictions:
