# Hypotheses (written before any benchmark was run)

Written 2026-10-06 in Phase 0. No kernel has been timed at this point. Each hypothesis has a verdict column that will be filled in after the results exist. Verdict values: supported, partly supported, refuted, pending.

Assumptions behind the numbers (all from public knowledge of Apple big cores, not measured here, so they are themselves hypotheses): 4 NEON FP pipes of 128 bits each, 3 load ports and 2 store ports per cycle, clock about 4 to 4.5 GHz on the fastest tier, 128 B cache lines, DRAM bandwidth for a single thread well below the chip total.

Notation: lanes L = 4 (fp32), 2 (fp64), 4 (int32). AI = flops per byte moved (compulsory traffic, write-allocate ignored unless stated).

## How verdicts will be assigned

Supported: measured value falls inside the stated range. Partly supported: trend correct but value outside range or only for some dtypes/kernels. Refuted: trend or value contradicts the statement. Anomalies are recorded with a plausible cause marked unverified.

## Pilot disclosure (added after the Phase 1 smoke run, 2026-10-06)

The rows above were written first and are not edited. During Phase 1 a smoke run (`data/raw/smoke_phase1.csv`, `data/raw/smoke_phase1_unroll.csv`; 3 sizes, 15 samples per point) was executed to validate the harness. It was not an experiment, but it exposed facts that bear on several hypotheses, so they are disclosed here. Verdicts are left to the real experiments.

1. The assignment-defined scalar build (`-O3 -fno-vectorize -fno-slp-vectorize`) is not unrolled by clang for these loops: `scalar` and `scalar_nounroll` timed identically (about 1 loop iteration per cycle). H1 assumed an unrolled scalar loop. An explicit scalar build with `#pragma clang loop unroll_count(8)` (`scalar_unroll8`) is faster (SAXPY f32, N = 4096: 561 ns vs 899 ns per call). Speedups will be reported against `scalar_unroll8` as the primary (conservative) baseline and against `scalar` as secondary.
2. Plain `-O3` does vectorize the f32 dot product (remark: vectorization width 4, interleaved count 4), but with a strict in-order reduction, so the adds remain a serial chain. H4 and H16 assumed no vectorization at all. The statement to test becomes: vectorized, but no better than latency bound.
3. SAXPY f32 at a 1 GiB working set reached about 149 GiB/s from one thread with the vector build, higher than the 60 to 120 GB/s assumed in H13, and a 4 MiB (L2-sized) point showed about the same bandwidth. The locality sweep will examine this.

No hypothesis text was changed in response to these observations.

## Addendum, written after Phase 2 disassembly and before Experiment 3 (2026-10-06)

The disassembly of the auto SAXPY (`vecreports/VECTORIZATION.md`) shows three code paths: scalar only for N < 4, a 4-element vector loop for 4 <= N < 16, and a 16-element main loop followed by the 4-element loop and a scalar loop. Predictions for the tail study (refines H11):

| ID | Hypothesis | Verdict |
|----|-----------|---------|
| H11b | Time per element for N = 16k + r is lowest for r = 0 and rises with the number of epilogue iterations: r in 1..3 (scalar tail only) costs more than r in 4..12 that are multiples of 4, and r that mixes both a 4-element step and scalar steps is the worst. The sawtooth is visible below N of about 256 and fades above N of about 1024. | refuted (no mod-16 sawtooth in the residual for N = 250..265, 1020..1029, 4090..4111; residual varies by less than 1.5 ns, comparable to noise; below N = 64 the pattern is irregular and not tied to N mod 4 or 16 in a way I can read from the plot) - plots/exp3_tail_mod16.png |
| H11c | Time per call is an affine function of N for N >= 16 with an intercept (fixed cost: entry checks plus call) of about 5 to 15 ns at 4.58 GHz (24 to 70 cycles). | refuted (affine fit for N = 32..160 gives an intercept of 2.2 ns (about 10 cycles) for f32 auto; predicted 5 to 15 ns; slope 0.0258 ns per element; the fit does not extrapolate to N >= 1000, where the residual is +13 ns at N = 1024 and +64 ns at N = 4096, i.e. per-element cost is higher than the small-N slope at large N because the small-N loop is faster per element) - data/processed/phase4_summary_phase4.txt |
| H21 | `auto_norestrict` SAXPY is within 10% of `auto` for non-overlapping arrays at large N (runtime check is a one-time cost), but is measurably slower for N below about 64 because of the check and branch. When the arrays are made to overlap by one element (y = x + 1), the runtime check sends execution to the scalar path and the speed falls to the scalar-build level. | partly supported (no-restrict build equals the restrict build within 7% at large N; at small N the runtime check costs 43% at N = 4 and 0 to 2% for N = 8 to 1024; with y = x + 1 it is far slower than the scalar build (9.4 to 12.8 cycles per element vs 1.0), not equal to it; with y = x + 64 it equals the non-unrolled scalar build at 1.0 cycle per element) - plots/exp7_alias_restrict.png |

## Addendum 2, written after the Phase 4 kernels were compiled and inspected, before Experiments 3 and 4 were run (2026-10-06)

Inspection of the compiler output (`vecreports/summary.md`, remarks for `saxpy_s*` and `gather`) shows that at strides 2 to 32 and for the gather the default `auto` build does not vectorize ("the cost-model indicates that vectorization is not beneficial", it only interleaves the scalar loop 4x), and that the `auto_forcevec` build (`#pragma clang loop vectorize(enable)`) vectorizes using `ld2.4s` de-interleave at stride 2, 2-lane `zip1` code at stride 8, and lane-by-lane `ld1.s {v}[n]` for the gather, always with scalar or lane stores (NEON has no scatter). Predictions:

| ID | Hypothesis | Verdict |
|----|-----------|---------|
| H12b | `auto` at stride 2, 4, 8, 16, 32 and for the gather runs within 10% of `scalar_unroll8` at every size (both are scalar), so the SIMD speedup is 1.0x +/- 0.1. | partly supported (within 10% at every stride >= 2 and size, except the gather in L1: auto is 16% faster than scalar_unroll8 (0.136 vs 0.162 ns per element); both builds are scalar loops at strides >= 2) - data/processed/phase4_summary_phase4.txt |
| H12c | `auto_forcevec` is not faster than `scalar_unroll8` for strides >= 2 and for the gather, and is slower by 10% or more at stride 2 in L1 because of the lane stores. | partly supported (auto_forcevec is not faster than scalar_unroll8 in L1 and is 74% slower at s4 (0.291 vs 0.167 ns per element), 6% slower at s2; but at 512 MiB s2 it is 11% faster (0.178 vs 0.200), and equal elsewhere) - plots/exp4_stride_gather.png |
| H12d | In L1 (32 KiB footprint), time per element is nearly independent of the stride for the scalar-like builds (they are instruction bound), while at 8 MiB and above time per element grows with stride until the stride reaches one 128 B line (stride 32 for f32), where each element costs one full line fill; beyond that point it stays flat. Useful GiB/s therefore falls by about 1/stride between stride 1 and stride 32 in DRAM, and is about flat in L1. | partly supported (growth with stride in DRAM yes, but in L1 time per element is not independent of stride: 0.09 ns at s1 to 0.166 at s2, flat s2 to s8, then rising to 0.36 at s32; and growth continues past s16 with a jump of about 10x between s16 and s32, much more than the 2x in bytes per element) - plots/exp4_stride_gather.png |
| H12e | The random gather in DRAM (x of 256 MiB) is limited by memory-level parallelism, not instruction count: it is at least 5x slower per element than unit stride in DRAM and 1.0 to 1.5x slower in L1. | partly supported (DRAM gather 2.9 ns per element is 39x slower than unit stride (0.075), above the 5x floor; in L1 the gather is 3.2x slower than the vector unit-stride and 1.8x slower than unroll8 unit stride, above the predicted 1.0 to 1.5x) - plots/exp4_stride_gather.png |
| H10b | Alignment: for SAXPY f32 the throughput at offsets 0 to 124 B (any multiple of 4) differs from offset 0 by at most 5% in L1 and L2 and by at most 3% in DRAM for the vector build (`auto`), with the largest effect at offsets that are not multiples of 16 B. | refuted (same data as H10: up to 40% in L1, 24% in L2, 21% in DRAM, not 5 and 3%) - plots/exp3_alignment.png |
