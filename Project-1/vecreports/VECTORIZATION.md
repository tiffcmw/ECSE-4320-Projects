# Vectorization verification (Apple clang 21.0.0, arm64, NEON)

Evidence files: remarks `vecreports/remarks/<build>_<kernel>_<dtype>.txt`, loop bodies `vecreports/asm/<build>_<kernel>_<dtype>.s`, table `vecreports/summary.md` (all generated by `scripts/vecreport.py`). Flags per build are in `docs/METHODOLOGY.md`. Excerpts below are cut to the main loop body and annotated; full dumps are not reproduced.

## Reading the evidence

- Vector width: NEON registers are 128 bit. `.4s` = 4 x 32-bit lanes (fp32, u32), `.2d` = 2 x 64-bit lanes (fp64). Remark text "vectorization width: W, interleaved count: I" gives lanes per vector (W) and independent vector copies per iteration (I), so the main loop handles W x I elements: 4 x 4 = 16 (f32, u32) or 2 x 4 = 8 (f64) elements per iteration.
- FMA: `fmla.4s` / `fmla.2d` (vector fused multiply-add) and `fmadd` (scalar fused multiply-add). Present in every non-fast-math build because `-ffp-contract=on` allows contraction within `a * x[i] + y[i]`.
- Masking: NEON has no predicated (masked) vector operations; SVE is not available in non-streaming mode here. Remainders are handled by a separate shorter vector loop and a scalar loop, not by masks (see tail structure below).
- Unroll: scalar builds: `scalar` and `scalar_nounroll` do not unroll (1 element per iteration); `scalar_unroll8` unrolls 8x by pragma.

## Summary of what vectorized

From `vecreports/summary.md` (VF x IC from the compiler remark; "main-loop instr" counts instructions in the largest vector loop):

| kernel | dtype | auto / native result | fastmath result |
|--------|-------|----------------------|-----------------|
| saxpy | f32, f64, u32 | vectorized 4x4 (f32, u32) or 2x4 (f64); 4 `fmla` per 16 (8) elements | same |
| mul | f32, f64, u32 | vectorized, 4 `fmul.4s` per 16 elements | same |
| stencil | f32, f64, u32 | vectorized, unaligned neighbour loads (`ldur q`, `ext`) | same, with a different fmul/fmla split |
| dot | f32, f64 | vectorized 4x4 (2x4), but the reduction stays strictly in order: vector multiplies, scalar `fadd` chain | vectorized with four independent `fmla` accumulators |
| dot | u32 | vectorized with `mla.4s` and four accumulators, no fast-math needed | same |
| all | all | not vectorized in `scalar`, `scalar_nounroll`, `scalar_unroll8` (remark "loop not vectorized") | |

`native` (`-mcpu=native`, resolves to `apple-m4`) produced identical loop bodies to `auto` in all inspected cases (same instruction counts in `summary.md`).

## Annotated excerpts

### SAXPY f32, auto: perfectly vectorized main loop (`vecreports/asm/auto_saxpy_f32.s`)
Remark: `vectorized loop (vectorization width: 4, interleaved count: 4)`.
```
ldp   q1, q2, [x9, #-0x20]     ; x[i..i+7]   (16 B vectors, loaded in pairs)
ldp   q3, q4, [x9], #0x40      ; x[i+8..i+15], pointer += 64 B
ldp   q5, q6, [x10, #-0x20]    ; y[i..i+7]
ldp   q7, q16, [x10]           ; y[i+8..i+15]
fmla.4s v5, v1, v0[0]          ; y += x * a   (a broadcast from lane 0), 4 fp32 lanes
fmla.4s v6, v2, v0[0]
fmla.4s v7, v3, v0[0]
fmla.4s v16, v4, v0[0]         ; 4 independent FMAs = interleave count 4
stp   q5, q6, [x10, #-0x20]    ; store 8 results
stp   q7, q16, [x10], #0x40    ; store 8 more
subs  x11, x11, #0x10          ; 16 elements per iteration
b.ne  loop
```
12 instructions per 16 elements. f64 (`auto_saxpy_f64.s`) is the same shape with `fmla.2d` and `subs #0x8` (8 elements per iteration).

### SAXPY f32, scalar (`scalar_saxpy_f32.s`): the assignment-defined baseline is not unrolled
Remark: `loop not vectorized`.
```
ldr   s1, [x1], #0x4           ; x[i]
ldr   s2, [x2]                 ; y[i]
fmadd s1, s0, s1, s2           ; scalar FMA
str   s1, [x2], #0x4
subs  x0, x0, #0x1             ; 1 element per iteration
b.ne  loop
```
6 instructions per element and a taken branch per element. `scalar_unroll8_saxpy_f32.s` has 8 `fmadd` and 25 instructions per 8 elements (3.1 per element).

### Tail structure of the auto SAXPY (from the full disassembly, `objdump -d --disassemble-symbols=_kern_saxpy_f32_auto build/obj/auto/saxpy_f32.o`)
```
cmp  x0, #0x4 ; b.hs  -> else only the scalar loop (n < 4)
cmp  x0, #0x10; b.hs  -> else a 4-element vector loop (ldr q / fmla.4s / str q) then scalar (4 <= n < 16)
...main loop, 16 elements per iteration...
tst  x0, #0xc ; b.eq  -> remainder of 4..12 elements goes through the 4-element vector loop
scalar loop for the last n mod 4 elements
```
So there are three code paths: scalar only (n < 4), 4-wide loop (n < 16), and 16-wide main loop followed by the 4-wide loop and a scalar loop. There is no masking; each remainder level is a separate loop with its own entry cost. This is used for the tail study predictions (docs/HYPOTHESES.md, addendum).

### Restrict: the main variant has no runtime alias check, `auto_norestrict` does (`vecreports/asm/auto_norestrict_saxpy_f32.s`)
My first version declared `restrict` on local pointers and the compiler still emitted runtime overlap checks (`cmp x2, x9; b.hs`), because LLVM derives `noalias` from `restrict` only on function parameters. The loop now lives in an always-inlined function with `restrict` parameters; the overlap checks and the scalar fallback path disappeared from `auto` (`summary.md`: 12-instruction main loop, 2 loads and 4 `fmla`) and remain in `auto_norestrict` (51-instruction region with a scalar fallback). The `restrict` experiment (negative case) uses these two builds. The Phase 1 smoke data (`data/raw/smoke_phase1*.csv`) predate this fix and are kept only as pilot data.

### Dot product f32, auto: vectorized multiply, strict serial sum (`vecreports/asm/auto_dot_f32.s`, 38 instructions, first 24 shown)
Remark: `vectorized loop (vectorization width: 4, interleaved count: 4)` (no fast-math).
```
ldp   q1, q2, [x9, #-0x20]     ; 16 elements of x and 16 of y loaded as vectors
...
fmul.4s v1, v1, v5             ; products computed 4 at a time (vector multiply)
mov   s5, v1[3]                ; but each lane is extracted ...
mov   s17, v1[2]
mov   s18, v1[1]
...
fadd  s0, s0, s1               ; ... and added one by one, in source order,
fadd  s0, s0, s18              ;     to the single accumulator s0
fadd  s0, s0, s17              ;     (16 dependent fadds per iteration)
fadd  s0, s0, s5
```
The compiler vectorizes the multiplication but preserves the original floating-point summation order, so the loop-carried chain of `fadd` remains. The assignment text predicts that a float dot product will not vectorize without fast-math; on this clang it does vectorize, in this reduced form. The consequence is measured in Phase 3 and 5 (a vectorized loop whose throughput is set by `fadd` latency, not by lanes).

### Dot product f32, fastmath: four independent accumulators (`vecreports/asm/fastmath_dot_f32.s`, complete loop)
```
ldp   q4, q5, [x9, #-0x20]
ldp   q6, q7, [x9], #0x40
ldp   q16, q17, [x10, #-0x20]
ldp   q18, q19, [x10], #0x40
fmla.4s v0, v16, v4            ; acc0 += x*y, 4 lanes
fmla.4s v1, v17, v5            ; acc1
fmla.4s v2, v18, v6            ; acc2
fmla.4s v3, v19, v7            ; acc3: 16 partial sums in flight, summed after the loop
subs  x11, x11, #0x10
b.ne  loop
```
10 instructions per 16 elements. This reassociates the sum (16 partial sums), which changes the rounding; the numerical difference is quantified in the negative case (Phase 5).

### Dot product u32, auto: no fast-math needed (`vecreports/asm/auto_dot_u32.s`)
```
mla.4s v0, v16, v4             ; integer multiply-accumulate, 4 lanes, four accumulators
mla.4s v1, v17, v5
mla.4s v2, v18, v6
mla.4s v3, v19, v7
```
Integer addition is associative, so reordering is legal and the compiler does it by default. This contrasts directly with the f32 dot product above.

### 3-point stencil f32, auto: unaligned neighbours (`vecreports/asm/auto_stencil_f32.s`, 27 instructions, first 24 shown)
```
ldp  q3, q4, [x13, #-0x20]     ; x[i..i+7]       aligned-stride loads
ldur q7, [x13, #-0x18]         ; x[i-1..i+2]     unscaled (unaligned) offset load
ldur q16, [x13, #-0x8]
ldur q17, [x13, #0x8]          ; x[i+1..i+4]
ext.16b v18, v2, v7, #0xc      ; built from the previous vector (register shuffle instead of a reload)
fmul.4s v18, v18, v0           ; c0 * x[i-1]
fmla.4s v18, v1, v3            ; + c1 * x[i]
fmla.4s v18, v1, v7            ; + c2 * x[i+1]  (c0 = .25, c1 = c2 = .5 after factoring; see source)
stp  q18, q19, [x12, #-0x20]
```
The compiler uses shifted loads (`ldur`) and `ext` for x[i-1] and x[i+1]; no gather or scalar fallback. Unaligned vector loads are plain `ldur q`.

## Not vectorized (negative cases, evidence only)
- All three scalar builds for every kernel: `loop not vectorized` in `vecreports/remarks/scalar*_*.txt`.
- `auto_norestrict`: vectorized but guarded by runtime overlap checks with a scalar fallback; if the pointers do overlap at run time, the scalar path executes (timed in Phase 5).
